| 2026-09-01 | **Multi-job-code assignment rule:** a crew member may receive multiple assignments, including assignments from multiple job-code pools, when there are more tasks than available crew. | Restaurant workload can exceed headcount; membership in multiple eligible pools must not artificially cap assignments. | Crew workflow must show all assigned tasks with job-code context and test repeated assignments across pools. |
| 2026-09-01 | **Crew task grouping:** display a crew member's assignments grouped by responsible job code. | Multi-skilled crew need clear context when switching between work areas. | Crew page must render separate job-code sections while retaining every assignment and its completion state. |

| 2026-09-01 | **Crew assignment constraints:** assignment eligibility must be enforced from the person's allowed job-code memberships; a person can receive tasks only from a job-code pool they belong to. Availability is out of scope until schedule importing exists. | Prevents assigning work outside a crew member's qualifications/role scope without inventing availability data. | Crew and manager views must preserve job-code context; manager-managed constraints are authoritative until a schedule-import sprint. |
| 2026-09-01 | **Per-person task exclusions:** managers may exclude specific task templates for an individual in addition to job-code eligibility. | Managers know person-specific restrictions that are not represented by job code alone. | Generation and reassignment must reject excluded tasks; setup UI and tests must cover adding/removing exclusions. |
| 2026-09-02 | **Task exclusions are normalized by person and task-template ID.** | Task titles can change; constraints must remain attached to the task identity. | Add/remove/clear UI operates on stable IDs and eligibility checks query the normalized relationship. |
| 2026-09-02 | **Master task-list numbers are permanent visible task identifiers.** | Existing job-code lists are numbered and those numbers are used when creating a separate schedule. | Job-code list imports must preserve the number and manager/crew views must display it alongside the task title. |
| 2026-09-02 | **Weekly generation uses double randomization with repeat avoidance within eligibility constraints.** | Randomize task order and the eligible-person order, then avoid assigning the same person the same task as the previous posted week whenever another eligible person exists. Eligibility remains limited to active people who belong to the task's job-code pool and have no exclusion for that task. | The next assignment-generation sprint must enforce active status, job-code membership, and task exclusions server-side; use prior-week comparison as a preference/constraint; and test fallback behavior when no eligible alternative exists. |
| 2026-09-02 | **Sprint 006 scope is limited to randomized assignment generation.** | Fairer weekly rotation is the immediate priority and should be designed separately from master-list import/display. | Sprint 006 must not implement numbered master-list imports or schedule importing; those remain candidates for a following sprint. |
| 2026-09-02 | **Repeat avoidance compares only with the immediately previous posted week.** | The manager needs a practical week-to-week rotation rule without introducing long-term weighting or history policy. | Generation should inspect the prior posted week for same-person/same-task pairs; older weeks do not block assignment. |
| 2026-09-02 | **Randomization does not replace balanced workload distribution.** | The current job-code pool behavior already spreads task counts; the goal is rotation, not a new weighting system. | Sprint 006 must preserve balanced task counts within each pool while randomizing task order and eligible-person selection. |
| 2026-09-02 | **Weekly draft lifecycle allows full regeneration only before posting.** | The manager may reject an unsatisfactory draft, but posted work must remain an auditable record rather than being silently regenerated. | A week has one active draft at a time; regenerate replaces the entire unposted draft. After posting, generation is locked and only individual eligible assignment edits/swaps are allowed. |
| 2026-09-02 | **Posted-task edits remain inside the task's responsible job-code pool.** | A task belongs operationally to one job-code group; cross-pool reassignment would violate that context. | Individual edits/swaps after posting must select only active, non-excluded people who belong to the task's responsible job code. |
| 2026-09-02 | **Multi-job-code people are randomized independently per pool.** | A person may legitimately work in several operational groups and should not have one global position that biases every pool. | Each job-code pool gets its own randomized eligible-person order; the same person may appear at different positions across pools. |
| 2026-09-02 | **Draft replacement requires confirmation.** | Regeneration discards the current unposted draft, so it must not happen from an accidental click. | The manager must explicitly confirm before the entire draft is replaced. |
| 2026-09-02 | **Posting offers a grouped printable task list.** | The manager may need a paper task list for operations after publishing the week. | After posting, ask whether to print; the print view groups by job code, then person, and shows each assigned task with its master-list number. Declining print does not block posting. |
| 2026-09-02 | **Printing uses the standard browser print flow.** | Avoid adding a separate PDF-generation feature when the browser already supports printing and Save as PDF. | The grouped print-friendly page opens the normal system/browser print dialog; no custom PDF file generation is required. |
| 2026-09-02 | **Printed task lists support paper completion tracking.** | The printed list may be used on the floor when digital completion is not practical. | Put a blank checkbox before each task and provide signature space after the listed tasks. |
| 2026-09-02 | **Printed signature space is per person and remains optional.** | Each person's paper list needs its own accountability trail, while digital completion/reporting remains the system of record. | Add signature space after every person's tasks; printing is an optional paper-trail path and does not replace digital completion or reporting. |
| 2026-09-02 | **Sprint 006 includes minimal master-list number support for printing.** | The posted printout must show the permanent task number, but full numbered text-file import is a separate follow-up. | Add/store/display the task number needed by the print view in Sprint 006; defer numbered-list parsing and complete import UX to the following sprint. |
| 2026-09-02 | **Number/title mismatches require manual importer resolution.** | Master-list numbers are stable references; silently renaming a task because a later source file changed its title could alter an established task definition unexpectedly. | Numbered imports must flag an existing number whose title differs and must not auto-update it; the manager resolves the mismatch manually. |
| 2026-09-02 | **Omitted source numbers remain active.** | A missing row may be a partial list or source mistake; automatic deactivation could remove operational work unexpectedly. | Numbered imports report existing numbers missing from the source but leave those task templates active until the manager changes them manually. |
| 2026-09-02 | **Duplicate source numbers require importer review.** | Silently choosing one of two rows with the same stable number could attach the wrong task title or notes to a schedule reference. | Numbered imports flag duplicate numbers for manual editing and do not silently select a winner. |
| 2026-09-02 | **Numbered text imports use a selected job-code scope.** | Separate source lists are maintained per operational job code, so repeating the job code on every line adds unnecessary input and error risk. | The manager selects one job code before importing lines such as `1. Clean Fryers`; the parser applies that job code to every valid row. |
| 2026-09-02 | **Numbered CSV imports and exports use stable task-list columns.** | Managers need to move numbered lists between the system and spreadsheets without losing notes or job-code context. | Import CSV columns are `number,title,notes` under the selected job code; exports must include the job code and preserve number, title, and notes. |
| 2026-09-02 | **Export format follows the source workflow.** | A combined spreadsheet is convenient for backup and editing, while separate text lists match the restaurant's per-job-code master lists. | CSV export is one combined file with a `job_code` column; TXT export produces one numbered list per job-code group. |
| 2026-09-02 | **Numbered imports are partial-success operations.** | A single bad row should not block unrelated valid task-list updates, while every rejected row still needs an actionable importer message. | Apply valid rows immediately and flag mismatches, duplicate numbers, and malformed rows for manual correction. |
| 2026-09-02 | **Export inclusion follows operational purpose.** | CSV is the complete editable/backup representation, while TXT is the active working master list. | Combined CSV export includes active and inactive tasks with an `active` flag; grouped TXT export includes only active numbered tasks. |
| 2026-09-02 | **Host-PC operations are deferred until the host is available.** | The host machine needed for supervised hosting is not currently available. | Sprint 009 must complete locally testable security, recovery, configuration, email rendering, and workflow rehearsal; host installation, external monitoring, production SMTP, tunnel/access setup, and real scheduler registration are follow-up work. |
| 2026-09-02 | **Schedule integration is phased by data need.** | Initial assignment eligibility only needs a day-level answer: whether a person works that day. PDF can support that narrow use with manual review; exact times and analytics need structured data. | A future initial schedule sprint may use Harri PDF to detect day-level work availability. Defer time-window constraints, automated availability rules, and schedule analytics. Continue asking Harri for CSV/API export for the extended phase. |
| 2026-09-02 | **CSV imports may synchronize notes on an exact task match.** | CSV carries notes while TXT does not; matching number and title identify the same task without a title mismatch. | For CSV rows whose number and title match an existing task, update the notes from the import; TXT imports preserve existing notes. |
| 2026-09-02 | **CSV imports synchronize active status on an exact task match.** | The complete CSV export includes operational status and should be able to round-trip that state. | For CSV rows whose number and title match an existing task, apply the imported `active` flag; title mismatches still require manual resolution. |
| 2026-09-02 | **CSV import accepts both combined and selected-scope files.** | Combined exports need to round-trip directly, while per-job-code files are simpler to prepare and match the text workflow. | If a CSV row includes `job_code`, use that row value; otherwise require the manager-selected job code for the file. |
| 2026-09-02 | **Legacy unnumbered tasks can be linked by confirmed exact identity.** | Existing tasks created before numbered imports should not be duplicated when the source clearly identifies the same job-code/title pair. | If an existing task has no number and its job code and title match an imported row, propose attaching the number and require manager confirmation before applying it. |
| 2026-09-02 | **Task-title matching is whitespace/case normalized.** | Source files may differ in capitalization or accidental spacing without representing a different task. | Matching trims surrounding whitespace, ignores capitalization, and collapses repeated internal spaces; stored titles are not silently rewritten. |
| 2026-09-02 | **Punctuation changes require manual review.** | Punctuation may change the intended task wording and is not as safely attributable to source formatting as case or whitespace. | Differences such as `Clean Fryers` versus `Clean Fryers!` are flagged as title mismatches rather than auto-matched. |
| 2026-09-02 | **Leading-zero master numbers require manual review.** | `01` may be an intentional source-format convention or an accidental entry, and silently converting it could hide a list problem. | Values such as `01` are flagged as formatting errors rather than automatically normalized to `1`. |
| 2026-09-02 | **Numbered imports require consecutive numbering from 1.** | Gaps make the source list harder to audit and may indicate missing task data. | The importer validates that numbers are `1, 2, 3...`; missing numbers are flagged to the importing manager for correction. |
| 2026-09-02 | **Blank lines are ignored in numbered TXT imports.** | Blank lines are common in hand-maintained lists and carry no task data. | Ignore blank lines; flag every other non-numbered, nonblank line as malformed input. |
| 2026-09-02 | **Valid new numbered rows create active tasks by default.** | A valid master-list row represents an operational task unless the complete CSV explicitly marks it inactive. | New TXT rows and new CSV rows without an inactive flag are created active, with the selected/row job code and optional CSV notes. |
